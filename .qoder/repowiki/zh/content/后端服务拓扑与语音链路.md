# 后端服务拓扑与语音链路

> `server/` 不是一个服务，而是**三类进程**：两个 Python FastAPI 语音服务 + 一个 Node Fastify 发音评分代理，再加上 `client/app/api/*` 的 Next.js BFF。

## 1. 拓扑全貌

| 进程 | 端口 | 技术 | 职责 |
|------|------|------|------|
| `transcribe_server.py` | 8766 | FastAPI + faster-whisper | 语音→文字，自带 VAD 与词级时间戳 |
| `align_server.py` | 8765 | FastAPI + WhisperX | 已知文本→强制对齐，输出词级时间戳（**不做识别**） |
| Fastify SOE 代理（`src/`） | 8788 | Node 20 + Fastify 5 | 契约② 发音评分代理，多供应商归一 |
| Next.js BFF（`client/app/api`） | 3000 | Next Route Handlers | LLM/TTS/翻译/助记/云端 ASR，注入本机密钥 |

启动：`cd server && ./start.sh`（可选 `--server align|transcribe|both`、`--device cpu|cuda|auto`、`--port`）。Python 侧需 ffmpeg，`.venv` 约 7.5GB，可删（脚本自动重建）。模型走 HF 缓存，首次下载耗时。

浏览器调用链示例（导入素材转写）：
`/api/transcribe`（BFF）→ 云端 ASR（Qwen/MiMo）→ 若为 multimodal 模型无词级时间戳 → 调 `:8765/align` 强制对齐 → 失败则按比例分配时间戳降级 → 返回 `segments[]` 供字幕分页使用。`/api/transcribe/local` 则直接打 `:8766/transcribe` 走本机 faster-whisper。

Python 侧端点：`POST /align`（`audio` + `text` + `language` → `words[{word,start,end}]`）、`POST /transcribe`、`GET /health`；对齐服务另有 `GET /models` 列出各语言可用对齐模型。

## 2. Fastify SOE 代理（契约②）

- `src/index.ts`：`loadEnv()`（zod 校验）→ `buildApp()` → `listen` → SIGINT/SIGTERM 优雅关闭。
- `app.ts`：`bodyLimit 32MB`、`@fastify/multipart` 限 `files:1 / fileSize:25MB / fields:5`、CORS 白名单取 `CORS_ORIGIN`（逗号分隔）。
- 统一错误出口：`ApiError` 自带状态码；413 → `PAYLOAD_TOO_LARGE`；其余 4xx 保留状态补 `code`；未知归一 500 `INTERNAL`。响应信封恒为 `{ code, message, detail? }`。
- 唯一业务端点：`POST /api/v1/soe/evaluate`；探活 `GET /healthz` 返回 `soeProvider`（默认）与 `soeProviders`（已配齐凭据的实现集合）。
- **Provider 注册表**（`services/soe/index.ts`）：`mock` 恒在；`azure`/`tencent`/`iflytek` 仅在凭据齐全时注册。默认取 `SOE_PROVIDER`，请求可用 multipart 字段 `provider` 覆盖，还可带 `creds`（JSON）**请求级密钥**——与 env 合并后同名请求胜出、空串视为未提供，凭据不齐则回落注册表（未注册由路由报 503）。这正是前端 BFF 注入密钥的通道，所以**密钥既不进浏览器也不必填 env**。
- 三家实现都是 WebSocket 流式：Azure Pronunciation Assessment（首发主方案，`PhonemeAlphabet=IPA` 保证音素符号统一）、腾讯口语评测新版 OEN（`wss://soe.cloud.tencent.com`，`tencent-ws-auth.ts` 负责签名）、讯飞 ISE 流式版（`wss://ise-api.xfyun.cn/v2/open-ise`，`iflytek-xml.ts` 处理报文，`IFLYTEK_FRAME_INTERVAL_MS` 默认 40ms 分帧发送）。
- 各 provider 的原始字段由 `soe-mapper.ts` 归一为统一 `SoeEvaluateResponse{ total, accuracy, fluency, integrity, words[{text,score,errorType?,phonemes[]}] }`，屏蔽厂商差异。`integrity` 语义 = 完整度（已发音词/参考词比值），字段名沿用契约②。`errorType`（`None|Omission|Insertion|Mispronunciation`）是真实 provider 才填的 optional 字段，mock 不填。
- 上游超时/重试：`SOE_TIMEOUT_MS=10000`、`SOE_RETRY=1`。
- `wav-pcm.ts` 负责 WAV→PCM 头剥离，喂给只收裸 PCM 的供应商。
- 文档状态：`server/README.md` 已于 2026-11-02 同步（三家 provider 凭据要求、`creds` 机制、`pnpm test`、multipart 字段顺序警告），此前"tencent 占位未实施"的表述已废弃。

## 3. 前端侧的发音能力取舍（Kokoro / Qwen TTS）

- **Kokoro-82M 在浏览器侧跑**：`client/platform/kokoro-tts.ts`（门面：`KOKORO_VOICES`、`preloadKokoroModel`、`set/getKokoroModelId`、`generateKokoroTts`、`subscribeKokoroLoad`）+ `kokoro-worker.ts`（Worker 内实际推理）+ `kokoro-protocol.ts`（消息协议与加载阶段类型），依赖 `kokoro-js` + `@huggingface/transformers`（ONNX）。模型 ID 与本地存放目录由 `/api/settings/kokoro` 提供（默认 `onnx-community/Kokoro-82M-v1.0-ONNX`，缓存到 `~/.ping-eng/kokoro-models`），`/api/hf/[...path]` 作为模型文件代理，`/api/models` 列出可用模型。应用启动即预加载。
- 分句合成 → 逐句时长累计 → 直接得到句级时间轴并生成 SRT，**无需 ASR 对齐**（架构 ADR-7 的核心理由；落地位置从文档说的后端改到了浏览器）。
- 云端 TTS 走 `lib/llm/providers/dashscope-tts.ts`（Qwen 音频合成 `/services/audio/tts/SpeechSynthesizer`）与 `mimo-tts.ts`（`/chat/completions` 形态，音色 Mia/Chloe/Milo/Dean）。音色候选由 `/api/settings/llm-configs` 按 provider 派生。
- 翻译走 `lib/llm/chat-service.ts`（每 50 条一批，上限 500 条，方向 `en2zh|zh2en`，支持 `direction:'auto'` 由服务端抽样判定）。

## 4. 语音链路的格式铁律

`core/audio/wav-encoder.ts`（`TARGET_SAMPLE_RATE = 16000`、`encodeWav`）+ `platform/recorder.ts` 恒定产出 **16kHz 单声道 WAV**（架构 ADR-5）。同一份录音可同时用于 ASR 转写与 SOE 评分，不需要多套录音配置，也不需要后端转码。任何"评分/识别结果异常"的排查都应先确认送进去的音频是否符合该格式（SOE 代理只认 wav/pcm 16k mono，`wav-pcm.ts` 会剥头，格式不符即上游报错）。
