# 项目总览

> 最后校准：基于仓库当前代码（`client/`、`server/`、`docs/`）实读，非文档转抄。2026-11-02 已完成一轮文档修正，见 `/开发指南与项目陷阱` §8。

## 1. 产品定位

**ping-english-assistant（英语精听助手）** 是一个本地优先（local-first）的英语学习应用，围绕「一段音视频 + 一份句子级字幕」展开训练：逐句精听 → 单句听写 → 跟读评分 → 影子跟读/背诵报告 → 生词本与助记。

交付形态为 **PC Web + 移动 H5 的单页应用**，数据全部落在浏览器 IndexedDB，后端（BFF / 代理服务）保持无状态。

## 2. 三个顶层工程

| 目录 | 性质 | 技术栈 |
|------|------|--------|
| `client/` | 正式前端工程 | Next.js 16.3 App Router 作 SPA shell + React 19 + TS 5.7.3 + Tailwind 4 + shadcn/ui(base-nova) + `app/api/*` BFF |
| `server/` | 后端能力集合 | Python FastAPI（faster-whisper 转写 :8766、WhisperX 对齐 :8765）+ Node.js Fastify 5（SOE 发音评分代理 :8788） |
| `page-prototype/` | 独立原型沙箱 | Next.js + React，仅设计迭代，无测试，与 `client/` 互不影响 |

`docs/` 是中文设计文档集（架构、原型、技术选型、各功能开发方案）。其中 `docs/系统架构设计.md` 是**契约与数据模型**的 ADR 级真源；自 v1.3 起文档内自带 §1.5「实现校准」，明确标出哪些拓扑描述已过时。

## 3. 关键认知：设计文档 ≠ 当前实现

这是本项目最容易踩坑的地方，务必区分两层：

- **`docs/系统架构设计.md` 描述的是规划中的生产形态**：uni-app（Vue 3）三端编译（PC Web / H5 / 微信小程序）+ Fastify 统一云出口 + Pinia + 条件编译适配层。
- **`client/` 实际落地的形态**是 Next.js SPA + React Router + 自研 store + **Next.js Route Handlers 充当 BFF**。因此：
  - 没有 uni-app、没有小程序端、没有条件编译；平台差异只需处理浏览器一种。
  - 没有 Pinia，状态层是 `stores/store.ts` 的 `createStore` + `useSyncExternalStore`。
  - 架构文档里的「后端统一出口」职责被**拆分**了：LLM/TTS/翻译/助记与云端 ASR 走 `client/app/api/*`（Next BFF），发音评分（契约②）走 `server/` 的 Fastify SOE 代理，本机转写/词级对齐走 `server/` 的 Python 服务。

`docs/系统架构设计.md` 中的 **API 契约编号（契约②⑤⑥⑦⑧）与数据模型定义仍被代码沿用**，代码注释里普遍以「真源：docs/系统架构设计.md §X」回链，所以文档不是废弃的，而是**契约与模型的规范来源、拓扑的过时描述**。

## 4. 端到端主链路

```
导入材料（音频/视频 + SRT/LRC，或本地/云端转写生成字幕）
  → IndexedDB 存 mediaRef(Blob key) + 已解析 SubtitleData
  → Player 页：SentencePlayer 逐句播放 / A-B 循环 / 字幕高亮
  → Training Center：五种模式
      puzzle(九宫格拼句) · dictation(单句听写) · read-aloud(跟读评分)
      shadowing(影子跟读) · recitation(全文背诵)
  → 录音统一 16kHz 单声道 WAV（core/audio/wav-encoder + platform/recorder）
  → 评分：BFF /api/soe/evaluate → Fastify 代理 → Azure/腾讯/讯飞
  → 分析：BFF /api/* → DashScope(Qwen) / MiMo LLM 流式返回
  → 生词本 / 助记卡片：/api/mnemonic → LLM 结构化 JSON
  → 配音：浏览器内 Kokoro-82M（Web Worker）或云端 Qwen/MiMo TTS
```
