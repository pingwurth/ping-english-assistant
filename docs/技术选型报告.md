# 英语学习助手 · 技术选型报告

> 本报告整合《播放组件与字幕解析方案调研报告》与《跨端适配策略与训练模式技术链路调研报告》两份调研成果，面向评审交付。所有对比数据与结论均来自原始调研，未做臆造。

---

## 概述与需求摘要

### 产品定位

一款支持 **PC Web、移动 H5、微信小程序** 三端的英语精听/跟读学习助手：用户导入本地音视频与字幕文件（.srt / .lrc），通过逐句播放、双语字幕与多种训练模式（九宫格、单句听写、跟读评分、影子跟读、全文背诵）进行学习。

### 关键功能诉求

| 需求点 | 说明 |
|--------|------|
| 逐句精听 | 上一句/下一句跳转，需精确 seek 到句子起始时间点 |
| 单句循环 (A-B Loop) | 在句子级别的起止时间区间内循环播放 |
| 倍速播放 | 0.5x ~ 2x |
| 双语字幕 | 支持 中文 / 英文 / 中英同时显示 三种模式切换 |
| 字幕滚动同步 | 独立字幕列表区域，一句一行，当前句高亮，自动滚动跟随 |
| 训练模式集成 | 九宫格、单句听写、跟读评分、影子跟读、全文背诵——均需逐句控制与录音能力 |
| 三端支持 | PC Web、移动 H5、微信小程序 |
| 本地文件导入 | 用户自行导入音视频文件和字幕文件 |

### 关键技术约束

- **微信小程序无法使用任何基于 DOM/Canvas 的 Web 播放器库**，必须使用原生 `<video>` 组件和 `InnerAudioContext` API。
- 用户明确要求：**优先选用成熟开源实现**，可扩展、可二次开发即可；多方案时给出优劣分析。
- 训练模式涉及录音、ASR、发音评分、LLM 分析，存在密钥安全与小程序域名白名单约束，**必须搭建后端**。

### 1.2 逐项优缺点分析

| 方案 | 优点 | 缺点 | 句子级控制能力 |
|------|------|------|---------------|
| **Video.js** | 生态最成熟，插件丰富（videojs-abloop 提供 A-B 循环），社区庞大，文档完善 | 体积较大（v8 ~75KB gzip，全量含 VTT 解析可达 225KB min），UI 定制成本偏高，对本项目简洁诉求过重 | `currentTime` + `timeupdate` + abloop 插件可实现，但需自行维护句子边界逻辑 |
| **Plyr** | 轻量(~18KB)，UI 简洁现代，API 清晰 | 维护活跃度下降（最后提交约 8 个月前），无内置 A-B loop，扩展性不如 Video.js，不支持自定义控件插槽 | 需完全自研（`plyr.currentTime` + `timeupdate`） |
| **xgplayer** | 字节跳动出品并大规模使用，组件化设计，插件体系灵活，按需加载，移动端优化好，中文文档完善，TS 支持良好 | 国际社区较小，npm 下载量偏低（23.6K/周），英文文档不如 Video.js | API 完善，组件化架构便于扩展自定义控件，A-B loop 实现较直接 |
| **DPlayer** | 弹幕功能出色，体积小，中文生态 | **项目基本停滞**（2024.2 最后提交），面向弹幕场景而非教育场景，扩展性有限 | **不推荐**：维护风险过高 |
| **ArtPlayer** | 体积小(~25KB)，高度可定制（自定义控件/图层/右键菜单），内置字幕支持(.vtt/.srt/.ass)，中文作者活跃维护 | 社区相对较小（6.2K stars），生态插件较少，部分高级需求需深入源码 | API 简洁，自定义控件极为方便，适合教育类深度定制 |
| **Howler.js** | 超轻量(7KB gzip)，Web Audio API 毫秒级精度，sprite 功能天然支持音频片段截取，跨浏览器兼容优秀 | 仅支持音频，维护节奏放缓 | sprite 定义 `[startMs, durationMs, loop]` 后可直接循环指定区间，天然适合 A-B loop |
| **原生 `<video>`/`<audio>`** | 零依赖零体积，完全控制 API，`currentTime` 毫秒精度 | UI 需完全自建，跨浏览器样式差异需处理 | 原生 API 完全满足 |
| **小程序原生** | `video` 支持 `seek(position)`、`playbackRate`、`bindtimeupdate`（约 250ms）；`InnerAudioContext` 支持 `seek`、`playbackRate`、`onTimeUpdate`（约 100-250ms） | 回调频率受系统限制（非每帧），seek 实际精度约 100ms；无法运行任何第三方 Web 播放器库 | 小程序端**唯一方案**，通过 `onTimeUpdate` + `seek()` 实现句级控制 |

### 1.3 推荐架构：统一播放控制抽象层 + 平台分别实现

```
┌─────────────────────────────────────────┐
│       统一播放控制层 (PlayerController)    │
│  play() / pause() / seekTo(ms)          │
│  setLoop(startMs, endMs) / setRate()    │
│  onTimeUpdate / onSentenceChange        │
│  getCurrentSentence() / next() / prev() │
└─────────────┬───────────────────────────┘
              │
    ┌─────────┼──────────┐
    ▼         ▼          ▼
 H5 Web     H5 Web    微信小程序
 (视频)     (音频)    (video/audio)
```

### 1.4 推荐结论

| 平台 | 视频场景 | 音频场景 | 理由 |
|------|---------|---------|------|
| **PC Web + 移动 H5** | **ArtPlayer**（首选），xgplayer 备选 | **Howler.js**（首选），原生 `<audio>` 备选 | ArtPlayer 轻量、高度可定制、内置字幕支持；xgplayer 移动端优化更强。Howler.js 音频精度出色且 sprite 天然适配 A-B loop |
| **微信小程序** | 原生 `<video>` 组件 | `InnerAudioContext` | 唯一选择；需后台播放时可用 `BackgroundAudioManager` |

**推荐理由细化**：

1. **ArtPlayer 作为 H5 视频首选**：25KB 体积适合移动端；自定义控件 API 极其灵活（添加"上一句/下一句/循环"按钮仅需几行代码）；内置 .srt 字幕渲染（可关闭转用自研字幕层）；活跃维护，中文作者响应快。
2. **Howler.js 作为 H5 音频首选**：7KB 超轻，Web Audio API 毫秒级精度；`sprite` 功能天然实现 A-B loop；纯音频场景无需视频播放器的重量。
3. **统一控制层必要性**：三端 API 差异大但行为语义一致，抽象层封装 `seek/loop/rate/timeUpdate` 后，上层业务代码（句子管理、训练模式）可完全复用。

## 二、字幕解析与展示

### 2.1 双语字幕格式分析

基于实际样本文件 `audio_原文和译文.srt`，格式为标准 SRT，双语方式是**同一字幕块内英文行在上、中文行在下**（换行分隔）：

```
1
00:00:02,610 --> 00:00:09,200
You should answer the questions as you listen...
你应该边听边回答问题...
```

这是最常见的双语 SRT 格式，解析时需按行拆分识别中英文。

### 2.2 候选方案对比

| 维度 | subtitle (npm) | srt-parser-2 | subsrt | lrc-kit / lrc-parser | 自研解析器 |
|------|---------------|--------------|--------|---------------------|-----------|
| **npm 周下载** | ~34,251 | ~2,000 | ~1,500 | <100 | N/A |
| **SRT 支持** | 优秀（含流式解析） | 良好（容错强） | 良好 | 不支持 | 按需 |
| **LRC 支持** | 不支持 | 不支持 | 支持 | 支持 | 按需 |
| **双语处理** | 无（需自行拆分） | 无（返回原始文本块） | 无 | 无 | 完全可控 |
| **输出结构** | `{start, end, text}` | `{id, startTime, endTime, text}` | 类似 | `{time, text}` | 自定义 |
| **格式容错** | 好（WebVTT 也支持） | 好（逗号/点分隔符均兼容） | 一般 | 一般 | 按需 |
| **TypeScript** | 有类型 | 有类型 | 无 | 部分 | 完全可控 |
| **体积** | ~5KB | ~3KB | ~8KB | ~2KB | ~1-2KB |
| **小程序兼容** | 可用（纯 JS） | 可用（纯 JS） | 可用 | 可用 | 可用 |

**各方案要点**：`subtitle` 下载量最高但不支持 LRC 且 API 偏 Node 风格；`srt-parser-2` 容错强但仅 SRT；`subsrt` 多格式但类型支持差、维护低活跃；LRC 专用库生态极小、多数年久失修。**没有任何现有库直接支持双语行拆分**，用任何库都需二次处理。

### 2.3 推荐结论：自研 SRT + LRC 解析器

1. **格式本身极简**：SRT 核心解析约 50-80 行代码，LRC 约 30-50 行；
2. **双语是核心需求**：双语拆分逻辑无论如何都必须自研；
3. **数据模型完全贴合业务**：直接输出满足"逐句控制"的结构；
4. **零依赖三端通用**：纯 TypeScript 实现，Web/H5/小程序完全通用；
5. **现有库价值有限**：引入 srt-parser-2 仅省下约 50 行代码，却增加依赖和不可控性。

**自研成本估计（约 1-1.5 天）**：

| 工作项 | 预估工时 |
|--------|---------|
| SRT 解析器（时间戳解析、多行文本、容错） | 2-4 小时 |
| LRC 解析器（时间标签、多格式兼容） | 1-2 小时 |
| 双语拆分逻辑（中英文行识别 + 对齐） | 1-2 小时 |
| 统一句子数据模型定义 | 1 小时 |
| 单元测试（覆盖边界用例） | 2-3 小时 |

### 2.4 句子级字幕数据模型

```typescript
/** 单个字幕句子 */
interface SubtitleSentence {
  /** 句子序号，从 0 开始 */
  index: number;
  /** 起始时间（毫秒） */
  startMs: number;
  /** 结束时间（毫秒） */
  endMs: number;
  /** 英文原文 */
  textEn: string;
  /** 中文译文（可为空，如纯英文字幕） */
  textZh: string | null;
  /** 英文按空格拆分的单词数组（供九宫格训练用） */
  words: string[];
}

/** 字幕文件解析结果 */
interface SubtitleData {
  /** 来源格式 */
  format: 'srt' | 'lrc';
  /** 是否包含双语 */
  isBilingual: boolean;
  /** 句子列表，按时间排序 */
  sentences: SubtitleSentence[];
  /** 总时长（毫秒） */
  totalDurationMs: number;
}
```

**该模型直接支撑所有业务场景**：

| 业务场景 | 模型使用方式 |
|---------|-------------|
| 逐句跳转 | `sentences[currentIndex ± 1].startMs` → seek |
| 单句循环 | `{startMs, endMs}` → A-B loop 区间 |
| 当前句高亮 | `onTimeUpdate` 时二分查找 `currentMs` 落入哪个句子 |
| 列表滚动同步 | 当前句 index 变化时滚动到对应元素 |
| 中英切换 | 根据模式显示 `textEn` / `textZh` / 两者 |
| 九宫格训练 | 直接使用 `words` 数组随机打乱 |
| 单句听写 | 播放 `[startMs, endMs]` 区间后等待输入 |

### 3.1 候选框架维护状态筛选

### 3.2 核心维度对比

| 对比维度 | Taro 4 (React) | uni-app (Vue 3) | 原生小程序 + 独立Web |
|---------|----------------|-----------------|---------------------|
| **三端代码复用率** | 70-85%（跨端组件/API 统一，平台差异需条件编译） | 75-90%（编译时优化+条件编译，插件市场有大量原生模块） | 0%（两套代码，仅后端 API 复用） |
| **小程序渲染性能** | 中等偏下 — 运行时方案，多一层虚拟 DOM→小程序 DOM 映射，setData 量较大 | 较好 — 编译时优化，模板静态化，setData 更精准 | 最优 — 原生无框架开销 |
| **音视频/录音封装** | `Taro.createInnerAudioContext`、`Taro.getRecorderManager` 等统一 API，高级控制仍需条件编译 | `uni.createInnerAudioContext`、`uni.getRecorderManager`，覆盖面类似，插件市场有 Recorder 跨端插件 | Web 端原生 Web Audio API 全能力；小程序端原生 API 无抽象损耗 |
| **社区生态** | GitHub 35k+ star，React 生态可复用，小程序专用组件库不如 uni-app 丰富 | 插件市场 6000+ 组件，中文社区最大，教程最多 | 分散，需各端独立维护 |
| **学习曲线** | 熟悉 React 的团队友好；需学 Taro 特有限制 | Vue 开发者零门槛；文档完善 | 需掌握两套技术栈 |
| **长期维护风险** | 京东持续投入，鸿蒙支持增加信心 | DCloud 商业公司持续投入，用户量大 | 无框架绑定风险，但人力成本翻倍 |

### 3.3 音视频/录音场景的跨端复用率关键发现

1. **播放器精准控制**：`InnerAudioContext.seek()` 在小程序端精度有限（部分安卓机存在几百 ms 偏差），Web 端 HTMLAudioElement 精度较好。无论 Taro 还是 uni-app，此平台差异都存在，需平台特定 workaround（如小程序端时间补偿算法）。
2. **录音格式差异**：Web 端 MediaRecorder 输出 webm/ogg（iOS Safari 仅支持 mp4/aac）；小程序 RecorderManager 支持 mp3/aac/pcm（无 webm）。必须做格式统一处理（推荐统一上传 PCM/WAV 到后端转码，或各端分别配置格式）。
3. **边播边录（影子跟读）**：Web 端可行，但浏览器默认回声消除会压低播放音量，需耳机或关闭回声消除；小程序端官方支持同时录播，但有回声串入风险，官方建议戴耳机或使用 `audioSource: 'voice_communication'`（有回声消除但音质下降）。
4. **条件编译影响评估**：音视频相关代码约占总业务代码 15-25%，但几乎 100% 需要平台条件编译或平台分支。跨端框架实际复用的是 UI 层（训练界面、列表、设置等）约 60-70% 的代码，而非核心音频处理逻辑。

### 3.4 推荐结论：uni-app (Vue 3)

1. **小程序性能最优**（编译时优化、setData 精简）——对逐句滚动等高频更新场景更有利；
2. **插件市场有成熟录音方案**（如跨平台 Recorder 插件，已处理回声消除、格式差异）；
3. **社区活跃度最高**，音视频问题的社区解决方案更丰富；
4. **三端复用率实际最高**（条件编译语法 `#ifdef MP-WEIXIN` 成熟易用）；
5. **学习曲线低**，Vue 3 + Composition API 对中型项目友好。

**次选：Taro 4 (React)** — 若团队 React 技术栈强烈偏好，需接受小程序端性能略逊、音视频社区资源稍少的 tradeoff。

**不推荐双代码库** — 本产品 UI 页面较多（播放器、字幕、多种训练模式、设置），双代码库维护成本过高，仅适合极端性能要求场景。

## 四、训练模式技术链路

### 4.1 录音采集

| 维度 | Web 端 (MediaRecorder / Web Audio API) | 微信小程序 (RecorderManager) |
|------|----------------------------------------|------------------------------|
| **兼容性** | Chrome/Edge/Firefox 全面支持；Safari 14.1+（iOS 14.5+） | 微信内置，无兼容问题 |
| **iOS Safari 注意点** | 仅支持 `audio/mp4` 容器（非 webm）；必须用户手势触发；采样率默认 44.1kHz | — |
| **输出格式** | Chrome: webm/opus；Safari: mp4/aac；可通过 Web Audio API 手动编码为 WAV/PCM | mp3, aac, pcm, wav（推荐 pcm 16kHz 供 ASR 使用） |
| **时长限制** | 无硬性限制（受内存约束） | 最长 10 分钟（600000ms） |
| **边播边录** | 可行；回声消除会压低播放音量；建议引导用户戴耳机 | 可行；需设置 `audioSource` 或引导耳机；有回声串入风险 |
| **推荐库** | Recorder.js (xiangyuecn) — 支持 MP3/WAV/PCM，兼容各浏览器含 iOS Safari | 原生 `wx.getRecorderManager()` 即可 |

**影子跟读边播边录最佳实践**：提示用户佩戴耳机 → 开启录音(PCM 16kHz) → 同时播放音频 → 录音结束后上传后端。不戴耳机场景接受一定回声混入，后端 ASR（Whisper 等）对轻微回声容忍度较好。

### 4.2 语音识别 ASR 方案对比

| 方案 | 价格 | 英文识别质量 | 流式支持 | 小程序可用性 | 适用场景 |
|------|------|-------------|---------|-------------|---------|
| **Web Speech API** | 免费 | 中等（依赖 Chrome 服务器） | 流式 | **不可用**（仅浏览器端） | Web 端听写的免费降级方案 |
| **OpenAI Whisper API** | $0.006/min（约¥0.04/min） | **最优** — 英文识别准确率极高 | 文件识别（非流式）；gpt-realtime-whisper 流式 $0.017/min | 后端调用→任何端可用 | 听写、影子跟读转写（推荐） |
| **讯飞语音听写** | ¥4-5/千次（约¥0.005/次） | 优秀 | 流式+文件 | SDK/WebSocket 均可 | 需要流式实时反馈时 |
| **腾讯云 ASR** | ¥2.4-3/千次 | 优秀 | 流式+文件 | 可用 | 与腾讯云生态结合 |
| **微信同声传译 (wechatSI)** | **免费** | 中等偏上（微信自研） | 流式 | **小程序专属插件** | 小程序端免费 ASR 首选 |
| **阿里云 ASR** | ¥2.5-3.5/千次 | 优秀 | 流式+文件 | 后端调用可用 | 备选 |
| **火山引擎** | ¥2-3/千次 | 优秀 | 流式+文件 | 后端调用可用 | 备选 |

**ASR 推荐策略（分端）**：

- **小程序端**：优先用 **wechatSI 插件**（免费、无需后端）做实时流式识别（单句听写场景）；
- **全端通用/高质量**：影子跟读和全文背诵上传录音文件到后端，调用 **OpenAI Whisper API**（英文识别准确率最高，性价比优）；
- **降级/备选**：讯飞 或 腾讯云（国内网络稳定性更好）。

### 4.3 发音评分方案对比

| 方案 | 评分维度 | 价格 | 小程序支持 | 接入方式 | 特点 |
|------|---------|------|-----------|---------|------|
| **腾讯云智聆 SOE (新版)** | 准确度、流利度、完整度、音素级 | 基础版 ¥4/千次起；后付费 ¥5/千次 | **有微信小程序 SDK** | REST API + 客户端 SDK | 小程序原生支持，中英文，微信生态最佳 |
| **讯飞 ISE** | 准确度、流利度、完整度、音素级、声韵调 | ¥6/千次（20万次套餐 ¥1200/年） | WebSocket API（需后端中转） | HTTP/WebSocket API | 评测标准最权威（国内考试标准制定者） |
| **Azure Pronunciation Assessment** | 准确度、流利度、完整度、韵律、音素级、内容评估 | $0.30/小时（约¥2.2/分钟） | 后端调用 | REST API + SDK | 评分维度最全，含韵律评估，适合高级场景 |
| **SpeechSuper** | 准确度、流利度、完整度、音素级 | $0.006/句 ($6/千次) | 后端 API 调用 | REST API + iOS/Android SDK | 国际化覆盖好，支持多语种 |

**推荐结论**：

- **首选：腾讯云智聆口语评测 (SOE)** — 有微信小程序原生 SDK，省去后端中转；价格最低（¥4/千次）；评分维度满足需求；中英文双支持。小程序端直接集成 SDK 减少链路延迟，Web/H5 端走后端 API 调用。
- **次选（高精度场景）：Azure Pronunciation Assessment** — 评分维度最丰富（含韵律 prosody），适合跟读评分要求极高的场景；缺点是价格较高、无小程序 SDK（需后端代理）。

### 4.4 LLM 交互

**使用场景**：影子跟读结束后分析 ASR 转写文本 vs 原文，给出发音问题分析和评分；全文背诵对比转写与原文，评估完整度、准确度并给出建议；可选的释义讲解功能。

**为什么必须通过自建后端**：

1. **密钥安全**：LLM API Key 不能暴露在前端/小程序代码中；
2. **小程序域名白名单**：微信小程序只能请求已备案域名，需代理到自建服务器；
3. **Prompt 管理**：评分 Prompt 模板应在服务端维护，便于迭代；
4. **速率控制与缓存**：后端可做请求合并、结果缓存、限流。

**接入方式**：后端（Node.js/Python）代理调用 OpenAI GPT-4o / Claude / 国产大模型（通义千问/GLM-4 等），通过 SSE 流式返回给前端。

### 4.5 各功能模块技术实现归属

| 功能 | 纯前端/原生 API 可实现 | 需第三方云服务 | 需自建后端 |
|------|---------------------|--------------|-----------|
| **九宫格选句** | 是（纯 UI 逻辑，前端拆词+拖拽） | 否 | 否 |
| **音视频播放/字幕同步** | 是（InnerAudioContext + 字幕解析） | 否 | 否（除非远程字幕文件管理） |
| **单句听写** | 部分 — 小程序端可用 wechatSI 免费识别 | Web 端建议用 Whisper/讯飞 | 是（如使用第三方 ASR API） |
| **跟读评分** | 录音前端完成；评分必须调服务 | **是** — 腾讯云 SOE / 讯飞 ISE / Azure | 是（Web/H5 端需后端代理；小程序端 SOE 可直连） |
| **影子跟读** | 录音+播放前端完成 | **是** — ASR 转写 + LLM 分析 | **是** — ASR API + LLM API 代理 |
| **全文背诵** | 录音前端完成 | **是** — ASR 转写 + LLM 分析 | **是** — ASR API + LLM API 代理 |
| **LLM 释义讲解** | 否 | **是** — LLM API | **是** — 密钥安全+域名白名单 |

### 4.6 端到端技术链路图

```
用户操作 → 前端录音(PCM/WAV)
    ├── 跟读评分 → 音频 → [小程序: 腾讯SOE SDK直连 / Web: 后端代理→SOE API] → 评分结果
    ├── 听写 → 音频 → [小程序: wechatSI插件 / Web: 后端→Whisper API] → 识别文本 → 前端对比
    ├── 影子跟读 → 音频文件 → 后端 → Whisper API → 转写文本 → LLM分析(vs原文) → 评分+建议
    └── 全文背诵 → 音频文件 → 后端 → Whisper API → 转写文本 → LLM分析(vs原文) → 评分+建议
```

### 5.2 选型之间的协同关系

各选型不是孤立决策，而是围绕 **"uni-app 承载三端 + PlayerController 屏蔽平台差异 + 后端收敛云服务"** 三条主线协同：

1. **uni-app 条件编译承载三端播放器适配层**：`PlayerController` 抽象接口用纯 TypeScript 定义，三个平台实现通过 uni-app 条件编译隔离——`#ifdef H5` 分支加载 ArtPlayer（视频）/ Howler.js（音频），`#ifdef MP-WEIXIN` 分支封装原生 `<video>` / `InnerAudioContext`。上层训练模式代码只面向抽象接口编程，与调研结论"音视频代码约占 15-25% 且几乎 100% 需条件编译、UI 层复用 60-70%"精确对应：把不可复用的部分收敛进适配层，把可复用的 UI/业务层最大化。

2. **自研字幕解析器是播放与训练模式的共同数据源**：`SubtitleSentence` 的 `startMs/endMs` 直接驱动 `PlayerController.seekTo/setLoop`（逐句跳转、A-B 循环）；`words` 数组直接供九宫格训练；`textEn/textZh` 支撑中英三态切换与滚动字幕。零依赖纯 TS 实现保证了它在 uni-app 三端编译产物中无兼容问题。

3. **ASR 分端策略与跨端框架呼应**：单句听写在小程序端走免费的 wechatSI 插件（条件编译引入），Web/H5 端走后端 Whisper 代理——同一份听写 UI 代码，识别能力按端分流，兼顾成本与质量。

4. **发音评分与微信生态协同**：腾讯 SOE 提供微信小程序原生 SDK，小程序端可直连减少延迟；Web/H5 端复用同一个后端代理通道。评分请求的音频来自统一约定的 PCM 16kHz 录音格式，该格式同时满足 SOE 与 Whisper 的输入要求，避免多套录音配置。

5. **后端是所有云服务的统一出口**：Whisper 转写、SOE 代理（Web 端）、LLM 分析共用一个轻量后端，同时解决密钥安全、小程序域名白名单、Prompt 管理与限流缓存四个问题；影子跟读/全文背诵的"录音 → ASR → LLM → 评分建议"链路完全在后端串联，前端各端只负责录音上传与结果展示。

## 六、风险与备选方案

| 风险项 | 影响 | 缓解措施 / 备选方案 |
|--------|------|---------------------|
| ArtPlayer 社区较小（6.2K stars），插件生态少 | 部分高级需求需深入源码 | 备选 xgplayer（字节维护、移动端优化更强）；PlayerController 抽象层使播放器可替换 |
| Howler.js 维护节奏放缓 | 长期依赖风险 | 备选原生 `<audio>`（API 足够满足句级控制）；抽象层同样保证可替换 |
| 小程序 `seek()` 精度有限（部分安卓机几百 ms 偏差），`onTimeUpdate` 回调仅约 100-250ms | 逐句跳转/循环边界不准 | 小程序适配层实现时间补偿算法；句子边界判断留容差 |
| 边播边录回声串入（影子跟读） | 录音混入播放声，影响 ASR/评分 | 引导用户佩戴耳机；小程序端 `audioSource: 'voice_communication'`；Whisper 对轻微回声容忍度较好 |
| 录音格式三端不一致（webm/mp4/pcm） | ASR/评分服务输入不统一 | 统一上传 PCM/WAV 到后端转码，或各端分别配置格式；Web 端用 Recorder.js 直接产出 WAV/PCM |
| wechatSI 识别质量中等 | 听写判定可能误伤 | 高要求场景切换到后端 Whisper 通道；前端对比算法留模糊匹配容差 |
| Whisper 为境外服务，网络稳定性风险 | 转写链路可用性 | 降级备选：讯飞语音听写 / 腾讯云 ASR（国内网络更稳） |
| 腾讯 SOE 评分维度不含韵律 | 高级评测场景不足 | 高精度场景备选 Azure Pronunciation Assessment（含 prosody，但价格较高、需后端代理） |
| uni-app 框架绑定风险 | 长期迁移成本 | DCloud 商业公司持续投入、用户量大；音视频模块独立封装、按平台分支实现，降低耦合 |
| 自研字幕解析器容错性 | 异常字幕文件解析失败 | 编写单元测试覆盖边界用例（已计入 2-3 小时成本）；参考 srt-parser-2 的容错策略（如 `.` 代替 `,` 分隔符） |
